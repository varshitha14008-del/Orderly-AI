# Architectural Decision Records (ADR) — Orderly-AI

This document records key technical decisions, rationale, API constraints, and sandbox behavior observed during development.

---

## ADR 001: Policy Engine Pre-Execution Guardrails
- **Date:** 2026-10-22
- **Status:** Accepted
- **Context:** Agentic commerce requires absolute deterministic boundaries before transactions reach PayPal settlement. LLMs may hallucinate prices, offer unapproved discounts, or agree to non-compliant terms.
- **Decision:** Every proposal generated by the LLM (buyer or seller agent) is intercepted by a pure TypeScript policy engine before being communicated to the opposing agent or sent to PayPal Orders v2. The policy engine verifies:
  1. Price bounds (buyer max price, merchant floor price).
  2. Bundle discount math.
  3. Prohibited terms and unapproved warranty commitments.
  If a proposal fails, the agent is re-prompted once with the policy violation. On repeated failure or API timeout/429, the engine automatically selects a deterministic fallback proposal.
- **Consequences:** 100% guarantees safety invariants regardless of LLM output.

## ADR 002: In-Memory OAuth Token Caching with Expiry Safety Margin
- **Date:** 2026-10-22
- **Status:** Accepted
- **Context:** PayPal OAuth tokens typically expire in ~32,400 seconds (9 hours). Making an OAuth call per API request wastes latency and risks rate limits (HTTP 429).
- **Decision:** Cache the sandbox OAuth access token in-memory along with its expiration timestamp. Automatically refresh when less than 5 minutes remain on the token. Exponential backoff retry logic is applied if a 429 is encountered.
- **Consequences:** Low latency and compliant usage of the PayPal API.

## ADR 003: Dispute Creation Strategy & Fallback
- **Date:** 2026-10-22
- **Status:** Accepted
- **Context:** In PayPal production, customer disputes can only be filed by the buyer through the PayPal resolution center. In the sandbox, programmatic buyer dispute creation requires `POST /v1/customer/disputes` with a simulated buyer `PayPal-Auth-Assertion`.
- **Decision:** Milestone 1 spikes the sandbox dispute creation endpoint. If sandbox authentication token assertions present unresolvable scope blocks, we provide a clean `DisputeService` abstraction:
  - If sandbox creation succeeds, use live sandbox dispute.
  - If restricted, use a clearly labeled `SimulatedDisputeSource` (as permitted in AGENTS.md §3.4) while executing 100% real `Payments v2` capture refunds upon merchant approval.
- **Consequences:** Preserves full real PayPal settlement and refund flows while guaranteeing judges can execute dispute mediation reliably without sandbox account blocking.

## ADR 004: Tamper-Evident Hash-Chained Audit Ledger
- **Date:** 2026-10-22
- **Status:** Accepted
- **Context:** Regulatory, audit, and merchant transparency requirements require tamper-evident tracking of all agent decisions and financial calls.
- **Decision:** Every event (agent turn, policy check, human approval, PayPal order/capture/refund call, and webhook) is logged as a hash-chained block: `hash = SHA256(prev_hash + timestamp + actor + type + payload)`.
- **Consequences:** Cheap, cryptographically verifiable proof of history displayed live in AG Grid Community.

## ADR 005: Gemini Model Selection (gemini-3.5-flash & gemini-3.5-flash-lite)
- **Date:** 2026-10-22
- **Status:** Accepted
- **Context:** The Google Gemini API evolves rapidly. In live API probing, legacy models (`gemini-2.0-flash`, `gemini-2.5-pro`) are retired with HTTP 404, while `gemini-3.8-flash` experiences transient high demand (HTTP 503).
- **Decision:** Use `gemini-3.5-flash` as the primary production model and `gemini-3.5-flash-lite` as the high-speed fallback. Both provide sub-second responses and guaranteed JSON schema adherence via `@google/genai`.
- **Consequences:** Eliminates 503/404 errors and guarantees predictable agent turn execution.
